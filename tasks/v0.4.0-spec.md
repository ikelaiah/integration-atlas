# Specification: v0.4.0 Historical Graph Comparison

## Objective and assumptions

Operators can compare the integration graph before and after an applied scan,
or compare checkpoints from two scans in the same workspace. A checkpoint is
the active graph at that instant, including manually maintained entities and
relationships. The comparison explains net additions, retirements and field
changes. Existing scans cannot be reconstructed accurately from their bounded
diff summaries, so they remain readable but have no selectable checkpoint.

## User flows

1. Apply a scan. Atlas saves before and after checkpoints in the same database
   transaction as the scan. Preview scans leave no checkpoint.
2. Open Scan history and choose two ordered checkpoints. The default pair is
   before and after the latest checkpointed scan. Inspect counts for entities
   and relationships, filter the changes by kind and action, and read old and
   new values for an updated row. A removed row uses its historical name.
3. Compare across multiple scans to see the net graph change, including a row
   added then removed between endpoints disappearing from the net result.
   Empty, loading, error, legacy-history, and truncated-list states are clear.

## Contract and storage

- Add a `scan_snapshots` table keyed by scan ID, with compact `before_json` and
  `after_json` graph values. `create_all` adds the table to an existing SQLite
  database without altering existing rows. No evidence, snippets, source paths
  or metadata are copied into snapshots. All captured text is redacted again.
- `GET /api/scans/checkpoints?workspace_id=...` lists completed, checkpointed
  scans in that workspace.
- `GET /api/scans/compare` requires workspace, two scan IDs and before/after
  phases. It rejects missing, cross-workspace, unfinished or unordered pairs.
  It returns exact totals and a bounded deterministic change list with
  `truncated` when more rows exist. Change fields show before and after values.
- Comparison reads persisted checkpoints only; it never rescans files and does
  not mutate current graph or review status.

## Implementation and verification

- Backend: add the table and capture/comparison service; wire the scanner and
  API; test first scan, multi-scan net changes, preview rollback, legacy scans,
  workspace isolation, order validation, bounds and redaction.
- Frontend: add a responsive comparison panel in Scan history with checkpoint
  selectors, summary, filters and field-level changes. Use the existing local
  API client and component styles.
- Docs: operator guide, ADR, README roadmap, version 0.4.0 and title-free
  release notes. Verify backend suite, Ruff, frontend type check/build,
  DocSprout check/audit/build, CI matrix, Docker smoke, GitHub Release and Pages.

## Commands and boundaries

- Test: `.venv/Scripts/python.exe -m pytest -q`
- Lint: `.venv/Scripts/ruff.exe check backend tests`
- Type check/build: `npm --prefix frontend run typecheck` and `npm --prefix frontend run build`
- Docs: `.venv/Scripts/docsprout.exe check`, `audit --strict`, and
  `build --release preview --output build/docs-site`.
- Preserve existing SQLite data and API behavior. Do not fabricate historical
  states for old scans. No new dependency, remote service or scanning agent.
