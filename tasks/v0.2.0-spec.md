# Specification: v0.2.0 Trust and Review

## Objective

Help an operator trust and correct an integration map before acting on it. The
operator can preview a scan's proposed changes, apply the scan, inspect the
actual diff, review evidence behind proposed relationships, and correct entity
details in the web UI. Atlas remains local and scans files statically.

## User flows and success criteria

1. In an existing workspace, enter a folder and preview a scan. Atlas shows
   added, updated, and retired entities and relationships, with names and a
   bounded list of changes. Preview does not alter the graph, evidence, scan
   history, or manual edits.
2. Apply the scan from the preview. Atlas scans the current files again, saves
   the actual diff in scan history, and makes clear when the result differs
   from the preview because files changed in between.
3. Open a review queue for a workspace. Filter proposed, confirmed, and
   rejected relationships; inspect their source, target, confidence, and
   redacted evidence; confirm or reject a proposal and optionally add a note.
   A later rescan preserves that verdict.
4. Edit an entity's descriptive fields from its detail panel. Atlas redacts
   inputs before persistence, records manual overrides, and retains them on
   later rescans. The graph and detail panel refresh after saving.
5. Scan history loads correctly and shows counts from the actual applied diff.

## API contract

- `POST /api/scans/preview` accepts `root_path` and an existing `workspace_id`.
  It returns scan statistics plus a bounded, redacted change list. It writes no
  durable rows.
- `POST /api/scans` applies a scan and returns `ScanProgress` with its actual
  `diff_summary`. `apply_changes=false` is rejected with a clear pointer to
  the preview endpoint; it must never silently apply changes.
- `GET /api/scans?workspace_id=...` returns the same `ScanProgress` shape used
  by `GET /api/scans/{id}` and the UI.
- `GET /api/review?workspace_id=...&status=...` returns a bounded list of
  active relationships with their entities and evidence.
- `POST /api/review/{relationship_id}` records a verdict and optional redacted
  manual note in one transaction. Existing entity edit endpoints remain the
  source of truth for manual overrides.

## Data and safety rules

- Reuse `Scan.diff_summary`, `ScanEvent`, entity `manual_fields_json`, and
  relationship `review_status`. No new table or database migration is planned.
- Preview and apply enforce the same path validation and scan-root allowlist.
- Change lists contain names, types, and redacted metadata, never raw file
  contents or secret values. Scanners never execute scanned artefacts.
- Preview and apply are separate operations. The apply result is authoritative
  because the folder may change between them.
- Rejected relationships remain stored for review history and are excluded from
  the default graph and impact analysis.

## Project structure

- `backend/atlas/scanners/`: discovery and normalisation.
- `backend/atlas/api/routes/`: HTTP contracts for scans and review.
- `backend/atlas/services/`: reusable diff logic.
- `frontend/src/features/scans/`: preview, apply, and history UI.
- `frontend/src/features/review/`: relationship review UI.
- `frontend/src/components/panels/`: entity editing in context.
- `tests/`: API and persistence regression tests.
- `docs/`: operator workflow and architecture decisions.

## Commands and code style

- Backend tests: `python -m pytest -q`
- Lint: `ruff check backend tests`
- Frontend type check: `npm --prefix frontend run typecheck`
- Frontend build: `npm --prefix frontend run build`
- Local demo: `atlas demo` then `atlas serve`

Use the existing Python type hints, Pydantic schemas, SQLAlchemy session
patterns, React function components, and typed API client. For example, a
route validates its workspace before querying rows and returns a named schema
instead of an untyped dictionary.

## Testing strategy

Write focused integration tests against the real SQLite session and HTTP API
for preview rollback, diff accuracy, applied scan history, review persistence,
manual override preservation, and redaction. Run the existing regression suite,
frontend type check and production build, then the repository CI matrix.

## Boundaries

- Always: preserve existing SQLite data; redact before persistence; keep the
  release body free of a repeated release title; publish only after green CI.
- Scope decision needed: whether the remaining README Phase 2 items also belong
  in v0.2.0. This spec uses the complete review and editing workflow as the
  working release scope.
- Avoid in this release: authentication, remote agents, automatic execution of
  scanned files, and changes to source files during a scan.

## Release completion

The backend and frontend identify as `0.2.0`; operator docs and release notes
match shipped behavior; a clean checkout can load the demo and use the new
workflow; CI passes; the `v0.2.0` tag points to the tested commit; the GitHub
Release body contains no release-title heading; DocSprout Pages deploys the
updated documentation.
